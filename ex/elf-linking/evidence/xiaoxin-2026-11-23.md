# 小新电脑实测记录：2026-11-23

实验位置：`from-scratch/operating-systems-lab/ex/elf-linking`。机器为 Intel Core i5-13500H，x86-64，Ubuntu `6.14.0-37.37~24.04.1-generic`，glibc `2.39-0ubuntu8.9`。以下为当次观察，地址和安装版本以后可能变化。

`make check` 通过了 ELF 元数据、三个程序算出 5，以及无共享库时三个分支的行为验证。

`make trace` 的关键事件顺序如下，文件名为便于阅读而缩写；完整跟踪可重新生成在 `build/traces/`：

```text
static:  execve(static) → [main] started → add(2,3) = 5
startup: execve(startup) → openat(libcalc.so) → [main] started → add(2,3) = 5
runtime: execve(runtime) → [main] started → [main] before dlopen
                       → openat(libcalc.so) → add(2,3) = 5
```

`readelf` 显示 `startup` 的 `DT_NEEDED` 包含 `libcalc.so`、`libc.so.6`，带 `BIND_NOW`；`runtime` 的 `DT_NEEDED` 不含 `libcalc.so`。`nm` 在静态可执行文件中显示已定义的 `add`。当次反汇编中，静态版本直接 `call 4018bc <add>`，启动时动态版本调用 `1070 <add@plt>`。

当次 GDB 在 `startup` 的 `main` 入口观察到：

```text
主程序基址             0x59d5c9817000
add@got.plt 槽地址     0x59d5c981afc0
槽中的值               0x7c72040330f9
&add                   0x7c72040330f9
libcalc.so 基址        0x7c7204032000
库中 add 偏移          0x10f9
```

此处 `0x7c7204032000 + 0x10f9 = 0x7c72040330f9`。GDB 捕获的是一次运行的用户态地址，不是固定物理地址。构建选项、工具链或 ASLR 改变后，偏移及地址可能不同。`LD_DEBUG=bindings` 也记录了 `startup` 到 `libcalc.so` 的 `add` 符号绑定。

把三个可执行文件复制到不含 `libcalc.so` 的独立目录后，静态程序成功；启动时动态链接程序在 `main` 前失败；运行时版本到 `dlopen` 处失败。测试未移动或删除原库。
